<script> 的 defer 和 async 有什么区别？ ​

这道题的关键不是背定义，而是能画出执行时序——面试官最想看的就是你对浏览器解析流程的理解。

先理解没有任何属性时发生了什么 ​

从时序图可以直接读出三者的本质差异：

普通 <script>：遇到标签就停下来，等下载完、执行完，才继续解析 HTML。下载和执行都会阻塞 HTML 解析。

async：下载和 HTML 解析并行进行，但下载完成后立即暂停 HTML 解析来执行脚本。执行时机不确定，取决于网络速度。

defer：下载和 HTML 解析并行进行，但执行被推迟到 HTML 完全解析完、DOM 构建好之后。DOMContentLoaded 事件在所有 defer 脚本执行完后才触发。

多个脚本时，顺序保证是关键差异 ​

async 的执行顺序完全由网络决定，小文件先下完就先执行，HTML 中的书写顺序无效。defer 无论哪个文件先下载完，都会等所有 defer 脚本下载完后按书写顺序依次执行。

三者核心对比 ​

普通 <script>asyncdefer
下载时是否阻塞解析是否否
执行时是否阻塞解析是是否
执行时机立即（下载后）下载完立即DOM 解析完成后
多脚本执行顺序有序不保证有序
能访问完整 DOM否（取决于位置）不保证是
适合放在 <head>会阻塞，不建议可以推荐

如何选择 ​

用 defer 的场景：绝大多数情况。需要操作 DOM 的脚本、有依赖关系的多个脚本（如先加载工具库再加载业务代码）、需要保证执行顺序时。现代框架构建产物多为 type="module"（见上文「进阶」），模块脚本默认延迟执行（行为类似带 defer 的经典脚本），在 HTML 解析完成后按文档顺序执行。

用 async 的场景：脚本完全独立，不依赖其他脚本，也不被其他脚本依赖，且不需要操作 DOM。最典型的例子是第三方统计脚本（Google Analytics、埋点 SDK），它们只需要尽早执行，不关心顺序，也不关心 DOM 是否准备好。

普通 <script>：如果必须放在 <head> 里，强烈建议加 defer 或 async；若放在 </body> 之前（传统做法），效果接近 defer，但现代项目已不推荐这种方式。

进阶：模块脚本 type="module" ​

打包工具（Vite、webpack 等）产出的入口常为 <script type="module">，与经典脚本不同：

  • 默认延迟执行：模块在 HTML 解析完成之后再跑，整体语义上接近「带 defer 的经典脚本」——不阻塞解析、按文档顺序执行多个模块依赖图。
  • 严格模式、顶层的 import / export、独立模块作用域；可加 async 表示并行取依赖、尽快执行（与经典 async 类似，但作用于模块图）。
  • 面试可答：「现代项目多 ES Module，默认不会在解析中途执行，和手写 defer 的经典脚本在「时机」上类似；细究规范时与 defer 仍不是同一套机制，不必背成一字不差。」

一个容易答错的追问 ​

"defer 脚本一定在 DOMContentLoaded 之前执行吗？"

是的。规范顺序是：先按文档顺序执行完所有 defer 脚本，再触发 DOMContentLoaded。因此单个 defer 脚本跑完时，事件还没派发。

那在 defer 脚本里监听 DOMContentLoaded 有用吗？有用：此时事件尚未触发，你在脚本里注册的监听器会在「全部 defer 脚本都执行完」之后被调用。若你只是要等「当前脚本执行时 DOM 已就绪」，一般不必再包一层 DOMContentLoaded，直接写逻辑即可；若你要在「页面上所有 defer 脚本都跑完」之后再做事（例如依赖后面某个 defer 脚本暴露的全局），用 DOMContentLoaded 仍然合理。

js
// 仅「DOM 已就绪」时，下面这层监听通常多余——直接写业务即可
document.addEventListener('DOMContentLoaded', () => {
  // 会执行：发生在所有 defer 脚本之后
});

// defer 保证执行到这里时文档已解析完，可直接操作 DOM
document.querySelector('#app').textContent = '已挂载';
